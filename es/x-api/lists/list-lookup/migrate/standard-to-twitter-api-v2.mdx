### List lookup: Standard v1.1 comparado con X API v2


Si has estado trabajando con los endpoints estándar v1.1 [GET lists/show](https://developer.x.com/en/docs/twitter-api/v1/accounts-and-users/create-manage-lists/api-reference/get-lists-show) y [GET lists/ownerships](https://developer.x.com/en/docs/twitter-api/v1/accounts-and-users/create-manage-lists/api-reference/get-lists-ownerships), el objetivo de esta guía es ayudarte a entender las similitudes y diferencias entre los endpoints estándar v1.1 y de X API v2 para List lookup.

* **Similitudes**
    * Métodos de autenticación
    * Rate limits
* **Diferencias**
    * URLs de endpoints
    * Requisitos de App y Project
    * Límites de objetos de datos por solicitud
    * Formatos de datos de respuesta
    * Parámetros de solicitud

#### Similitudes

**Autenticación**

Ambas versiones del endpoint admiten tanto [OAuth 1.0a User Context](/resources/fundamentals/authentication#oauth-1-0a-2) como [App only](/resources/fundamentals/authentication#app-only-authentication-and-oauth-2-0-bearer-token). Por lo tanto, si anteriormente usabas uno de los endpoints estándar v1.1 de List lookup, puedes seguir utilizando el mismo método de autenticación si migras a la versión de X API v2.

Dependiendo de tu biblioteca/paquete de autenticación preferido, la autenticación App only probablemente sea la forma más sencilla de empezar y se puede establecer con un encabezado de solicitud simple. Para aprender cómo generar un Access Token App only, consulta [esta guía de App only](/resources/fundamentals/authentication#using-and-generating-an-app-only-bearer-token).

**Rate limits**

|     |     |
| :--- | :--- |
| **Standard v1.1** | **X API v2** |
| /1.1/lists/show.json<br/><br/>75 solicitudes por ventana de 15 minutos con OAuth 1.0a User Context<br/><br/>75 solicitudes por ventana de 15 minutos con App only | /2/lists/:id<br/><br/>75 solicitudes por ventana de 15 minutos con OAuth 1.0a User Context<br/><br/>75 solicitudes por ventana de 15 minutos con OAuth 2.0 Authorization Code with PKCE |
| /1.1/lists/ownerships.json<br/><br/>15 solicitudes por ventana de 15 minutos con OAuth 1.0a User Context<br/><br/>15 solicitudes por ventana de 15 minutos con App only | /2/users/:id/owned_lists<br/><br/>15 solicitudes por ventana de 15 minutos con OAuth 1.0a User Context<br/><br/>15 solicitudes por ventana de 15 minutos con OAuth 2.0 Authorization Code with PKCE<br/><br/>15 solicitudes por ventana de 15 minutos con App only |

#### Diferencias

**URLs de endpoints**

* Endpoints estándar v1.1:
    * GET https://api.x.com/1.1/lists/show.json
        (Consulta una List especificada)
    * GET https://api.x.com/1.1/lists/ownerships.json
        (Consulta las Lists propiedad de un usuario especificado)
* Endpoint X API v2:
    * GET https://api.x.com/2/lists/:id
        (Consulta una List especificada)

    * GET https://api.x.com/2/users/:id/owned_lists
        (Consulta las Lists propiedad de un usuario especificado)

**Requisitos de App y Project**

Los endpoints de X API v2 requieren que uses credenciales de una [App de desarrollador](/resources/fundamentals/developer-apps) asociada a un [Project](/resources/fundamentals/developer-apps) al autenticar tus solicitudes. Todos los endpoints de X API v1.1 pueden usar credenciales de Apps o Apps asociadas a un project.

**Límites de objetos de datos por solicitud**

El endpoint estándar v1.1 /lists/ownerships te permite devolver hasta 1000 Lists por solicitud. Los nuevos endpoints v2 te permiten devolver hasta 100 Lists por solicitud. Por defecto, se devuelven 100 objetos de usuario; para cambiar el número de resultados deberás pasar un parámetro de consulta max_results= con un número entre 1-100; luego puedes pasar el next_token devuelto en el payload de respuesta al parámetro de consulta pagination_token en tu siguiente solicitud.

**Formato de datos de respuesta**

Una de las mayores diferencias entre las versiones estándar v1.1 y X API v2 del endpoint es cómo seleccionas qué fields se devuelven en tu payload.

Para los endpoints estándar, recibes muchos de los fields de respuesta por defecto y tienes la opción de usar parámetros para identificar qué fields o conjuntos de fields adicionales deben devolverse en el payload.

La versión de X API v2 solo entrega los fields id y name de la List por defecto. Para solicitar fields u objetos adicionales, deberás usar los parámetros [fields](/x-api/fundamentals/fields) y [expansions](/x-api/fundamentals/expansions). Cualquier field de List que solicites desde este endpoint se devolverá en el objeto List principal. Cualquier objeto expandido de Post o usuario y sus fields se devolverán en un objeto includes dentro de tu respuesta. Luego puedes emparejar los objetos expandidos con el objeto List coincidiendo los IDs ubicados tanto en el objeto de usuario como en el objeto de Post expandido.

Aquí hay ejemplos de posibles fields y expansions de List:

* created_at

* follower_count

* member_count

* owner_id

* description

* private


|     |     |
| :--- | :--- |
| **Endpoint** | **Expansion** |
| /2/lists/:id | owner_id |
| /2/users/:id/owned_lists | owner_id |

Te animamos a leer más sobre estos nuevos parámetros en sus respectivas guías, o leyendo nuestra guía sobre [cómo usar fields y expansions](/x-api/fundamentals/data-dictionary/reference#how-to-use-fields-and-expansions).

También hemos elaborado una [guía de migración de formatos de datos](/x-api/migrate/data-format-migration) que puede ayudarte a mapear fields estándar v1.1 a los nuevos fields v2. Esta guía también te proporcionará los parámetros expansion y field específicos que necesitarás pasar con tu solicitud v2 para devolver fields específicos.

Además de los cambios en cómo solicitas ciertos fields, X API v2 también introduce nuevos diseños JSON para los objetos devueltos por las APIs, incluyendo objetos [Post](/x-api/fundamentals/data-dictionary/reference#tweet) y [user](/x-api/fundamentals/data-dictionary/reference#user).

* En el nivel raíz del JSON, los endpoints estándar devuelven objetos Post en un array statuses, mientras que X API v2 devuelve un array data.

* En lugar de referirse a "statuses" Retweeted y Quoted, el JSON de X API v2 se refiere a Tweets Retweeted y Quoted. Se eliminan muchos fields heredados y deprecados, como contributors y user.translator_type.

* En lugar de usar tanto favorites (en el objeto Post) como favourites (en el objeto de usuario), X API v2 usa el término like.

* X está adoptando la convención de que los valores JSON sin valor (por ejemplo, null) no se escriben en el payload. Los atributos de Post y usuario solo se incluyen si tienen valores no nulos.

**Parámetros de solicitud**

Los siguientes parámetros de solicitud estándar v1.1 tienen equivalentes en X API v2:

**List lookup by ID**

|     |     |
| :--- | :--- |
| **Standard v1.1** | **X API v2** |
| list_id | id  |
| slug | Sin equivalente |
| owner\_screen\_name | Sin equivalente |
| owner_id | Solicitado con el parámetro expansions/fields |

**User owned List lookup**

|     |     |
| :--- | :--- |
| **Standard v1.1** | **X API v2** |
| user_id | id  |
| screen_name | Sin equivalente |
| count | max_results |
| cursor | pagination_token |
