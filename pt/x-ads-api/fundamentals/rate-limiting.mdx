A Advertiser API tem rate limit semelhante à REST API v1.1, como documentado aqui: [REST API Rate Limiting in v1.1](https://developer.x.com/content/developer-twitter/en/docs/basics/rate-limits). Diferentemente da REST API v1.1, não há um índice programático dos limites por endpoint. Os rate limits e janelas de reset dos endpoints são comunicados via headers de resposta HTTP. Todo o rate limiting na Ads API utiliza OAuth 1.0A.

## Limites em nível de usuário e nível de conta ad

Existem dois tipos de rate limits: nível de user token e nível de conta ad. Um subconjunto de endpoints está habilitado para usar rate limiting em nível de conta ad. Um user token é o [access token OAuth](/resources/fundamentals/authentication#obtaining-access-tokens-using-3-legged-oauth-flow) usado para autenticar e chamar a Ads API. Cada user token pode ter acesso a uma ou mais contas ad.

Desenvolvedores devem utilizar o rate limit em nível de conta ad quando ele for retornado nos headers de resposta e usar apenas o limite em nível de usuário quando o limite de conta ad não for encontrado.

Rate limits em nível de usuário são expressos por meio destes headers: **x-rate-limit-limit**, **x-rate-limit-remaining** e **x-rate-limit-reset**

Para endpoints com rate limiting em nível de conta ad habilitado, os rate limits são expressos por meio destes headers: **x-account-rate-limit-limit**, **x-account-rate-limit-remaining** e **x-account-rate-limit-reset**.

Os rate limits em nível de conta ad são fornecidos apenas para endpoints GET para permitir que as aplicações sincronizem dados de entidades (como objetos de campanha ou line item) de um único user token acessando múltiplas contas ad. Ações de write não são garantidas de usar os mesmos rate limits em nível de conta ad.

Para endpoints com rate limit em nível de conta ad, o rate limit em nível de usuário é definido em um valor alto que representa uma cota global para toda a sua aplicação. Quando disponível, o rate limit em nível de conta ad deve ter precedência no controle do volume de suas requisições.

## Melhores práticas

1) Salve um timestamp em seu banco de dados com o último timestamp sincronizado e, ao solicitar dados quando aplicável, solicite dados com a opção `sort_by=updated_at-desc` para permitir interromper seu processo de sincronização após atingir dados mais antigos que seu último timestamp sincronizado. Isso evitará sincronizar os mesmos dados redundantemente.

2) Solicite múltiplas entidades em uma única requisição: Alguns endpoints permitem especificar uma lista de valores separada por vírgulas para recuperar múltiplas peças de dados semelhantes. Isso pode reduzir o número total de chamadas feitas e, assim, aproveitar o rate limit de forma mais eficiente.

3) Solicite o "count" máximo em suas requisições: Alguns endpoints como [GET accounts/:account\_id/targeting\_criteria](/x-ads-api/campaign-management/reference#targeting-criteria) são fortemente recomendados a serem chamados com o valor máximo de count para retornar 1000 objetos em vez do padrão de 200.

## Perguntas frequentes

_É possível aumentar os rate limits para uma conta ad específica ou nossa aplicação?_

Geralmente não podemos aumentar os rate limits, pois eles são definidos para suportar as maiores contas ad. Implemente as Melhores Práticas listadas neste documento como primeiro passo, e se os rate limits ainda estiverem afetando sua capacidade de escalar ou atingir objetivos de negócio, entre em contato com seus contatos da X Ads API com detalhes completos sobre o caso de uso e requisições envolvidas.

## Escopos de rate limiting

### Escopos para este documento

* Categoria: todos os endpoints que se enquadram na categoria dada têm rate limit a partir de um único limite alocado por janela.
* Endpoint: cada endpoint tem seu próprio limite alocado distinto por janela.
