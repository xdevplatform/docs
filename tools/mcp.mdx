Two [MCP](https://modelcontextprotocol.io) (Model Context Protocol) servers are available for working with X from AI tools:

| Server | What it does | URL |
|:-------|:-------------|:----|
| **X MCP** | Call X API endpoints (search posts, look up users, bookmarks, trends, news, Articles, and more) | `https://api.x.com/mcp` (hosted; Streamable HTTP with OAuth discovery) |
| **Docs MCP** | Search and read X API documentation | `https://docs.x.com/mcp` (hosted) |

## X MCP — X API

Connect MCP-compatible AI tools such as Grok and Cursor directly to the **X API**. The model can then search the full archive, look up users, manage bookmarks, fetch trends and news, and draft Articles — all with your own X account's permissions.

The X API exposes a hosted **Streamable HTTP** MCP server at **`https://api.x.com/mcp`** (protocol `2025-06-18`, `serverInfo: xmcp`). It advertises standard MCP OAuth discovery metadata, so MCP clients with native OAuth support can connect directly using your X app's OAuth 2.0 Client ID. For clients without native OAuth support (or headless and multi-account workflows), you can also connect through the optional open-source **`xurl mcp`** local bridge.

### Capabilities at a glance

| Category | What the model can do |
|---|---|
| **Posts** | Fetch posts, see likers / reposters / quoters, recent counts |
| **Search** | Full-archive post search, user search, news search |
| **Users** | Resolve the current user, look up by id / handle, read a user's posts, timeline, and mentions |
| **Bookmarks** | List / add / remove bookmarks and manage bookmark folders |
| **News & Trends** | Get news stories, get trends for a location (WOEID) |
| **Articles** | Create draft Articles and publish them |

### How it works

`api.x.com/mcp` advertises standard MCP OAuth discovery (RFC 9728 Protected Resource Metadata and RFC 8414 Authorization Server Metadata):

- An unauthenticated `POST https://api.x.com/mcp` returns `401 Unauthorized` with `WWW-Authenticate: Bearer resource_metadata="https://api.x.com/.well-known/oauth-protected-resource"`.
- Protected Resource Metadata is served at `https://api.x.com/.well-known/oauth-protected-resource` (and the RFC 9728 path variant `https://api.x.com/.well-known/oauth-protected-resource/mcp`), advertising `authorization_servers: ["https://api.x.com"]`, `bearer_methods_supported: ["header"]`, and the supported OAuth 2.0 scopes.
- Authorization Server Metadata is served at `https://api.x.com/.well-known/oauth-authorization-server`, advertising `authorization_endpoint` (`https://x.com/i/oauth2/authorize`), `token_endpoint` (`https://api.x.com/2/oauth2/token`), PKCE (`S256`), `authorization_code` and `refresh_token` grants, and token endpoint auth methods `none` (public PKCE client) and `client_secret_basic`.

There is **no dynamic client registration** (`registration_endpoint` is not advertised), so you still create your own OAuth 2.0 app in the [X Developer Console](https://developer.x.com) and provide its **Client ID** to your MCP client.

```mermaid
flowchart LR
    A["MCP client<br/>(Grok, Cursor)"] -- "HTTPS + Authorization: Bearer" --> B[("api.x.com/mcp")]
    A <-- "OAuth discovery + PKCE S256 login & refresh" --> C["X OAuth<br/>(/.well-known/*, x.com, api.x.com)"]
```

If your MCP client does not support native MCP OAuth with a pre-registered Client ID, you can run the optional **`xurl mcp`** local stdio bridge instead — it handles the OAuth 2.0 PKCE login and token refresh locally and forwards requests over HTTPS with a fresh Bearer token.

### Getting started

Pick one of three routes:

* **Native OAuth 2.0 (recommended — direct URL).** Point an OAuth-capable MCP client directly at `https://api.x.com/mcp` with your X app's OAuth 2.0 Client ID. The client discovers the OAuth endpoints automatically, runs OAuth 2.0 PKCE (`S256`), and refreshes tokens. Works for reads and writes with your account's scopes.
* **App-only Bearer (direct URL, read-only).** Paste your app's Bearer token into an `Authorization` header on the MCP client. No browser login; read-only endpoints only, with no user context (can't act as you).
* **Optional: `xurl mcp` bridge (local stdio).** For MCP clients that don't support native OAuth with a pre-registered Client ID (or headless / multi-account setups), a local bridge handles the OAuth 2.0 PKCE login and auto-refreshes tokens.

#### Native OAuth 2.0 setup

1. **Create or reuse an X app** in the [X Developer Console](https://developer.x.com) with **OAuth 2.0** enabled.
2. **Choose the app type:** **Native App** (public client, PKCE only). Confidential clients (Web App / Automated App) also work with clients that use `client_secret_basic` (such as Grok Build), but never `client_secret_post`, which X rejects.
3. **Register the callback URI** for your client:

| Client | Callback URI to register |
|---|---|
| Grok Build (CLI) | `http://127.0.0.1:8080/callback` (must be `127.0.0.1`, not `localhost`) |
| Grok (web) | `https://grok.com/connectors-oauth-exchange-code/` |
| Cursor (Desktop app) | `http://localhost:8787/callback` |
| Cursor (Web / Cloud Agents) | `https://www.cursor.com/agents/mcp/oauth/callback` |

4. **Copy your OAuth 2.0 Client ID** from the app's **Keys and tokens** page (the long string, not the numeric app ID).

#### App-only Bearer setup (read-only)

1. **Create an X app** in the [X Developer Console](https://developer.x.com).
2. **Copy your App-only Bearer token** from the app's **Keys and tokens** page.
3. Point your client at `https://api.x.com/mcp` with the token as an `Authorization` header — see [App-only (direct URL)](#app-only-direct-url) below.

#### Optional: `xurl mcp` bridge setup

Use this route if your MCP client does not support native MCP OAuth with a pre-registered Client ID, or if you want headless / multi-account CLI auth:

1. **Create an X app** with **OAuth 2.0** enabled.
2. **Register the redirect URI** `http://localhost:8080/callback` on the app (required for the first-run browser login). To use a different one, set `REDIRECT_URI` and register that instead.
3. **Copy your `CLIENT_ID` and `CLIENT_SECRET`** — you'll put them in the client config. If you ever run `xurl auth oauth2` manually (e.g., the headless flow below), export them as environment variables in that shell first — the login fails in the browser without them.
4. **Have Node.js installed** (for `npx`), or install **[xurl](https://github.com/xdevplatform/xurl)**:

   ```bash
   brew install --cask xdevplatform/tap/xurl      # Homebrew
   npm install -g @xdevplatform/xurl              # npm (global)
   curl -fsSL https://raw.githubusercontent.com/xdevplatform/xurl/main/install.sh | bash
   ```

<Note>
**First login needs a browser.** On a headless/remote box, authenticate out-of-band first with `xurl auth oauth2 --headless` (paste-a-code flow), then the bridge just reuses the cached token. See [Headless](/tools/mcp#headless--remote-machines).
</Note>

### Connect your client

#### 1. Grok Build (CLI)

Add to `~/.grok/config.toml` (for native OAuth, keys under `.oauth` must be camelCase):

<CodeGroup>

```toml Native OAuth (~/.grok/config.toml)
[mcp_servers.xapi]
url = "https://api.x.com/mcp"
enabled = true

[mcp_servers.xapi.oauth]
clientId = "YOUR_OAUTH2_CLIENT_ID"
callbackPort = 8080
scopes = ["tweet.read", "users.read", "bookmark.read", "bookmark.write", "offline.access"]
```

```toml App-only Bearer (~/.grok/config.toml)
[mcp_servers.xapi]
url = "https://api.x.com/mcp"
enabled = true

[mcp_servers.xapi.headers]
Authorization = "Bearer YOUR_APP_ONLY_BEARER_TOKEN"
```

```toml xurl bridge — optional (~/.grok/config.toml)
[mcp_servers.xapi]
command = "npx"
args = ["-y", "@xdevplatform/xurl", "mcp", "https://api.x.com/mcp"]
enabled = true
startup_timeout_sec = 300          # give the first-run browser login time

[mcp_servers.xapi.env]
CLIENT_ID = "YOUR_X_APP_CLIENT_ID"
CLIENT_SECRET = "YOUR_X_APP_CLIENT_SECRET"
```

</CodeGroup>

For **Native OAuth**, include `offline.access` in `scopes` so tokens refresh automatically, and pick only the X API scopes your agent needs (from the server's advertised `scopes_supported`). No secret is needed with a Native App; if you use a confidential app, add `clientSecretEnvVar = "X_MCP_CLIENT_SECRET"` and export that variable in the same shell. Run `grok` → `/mcps` → select `xapi` → press `i` to complete the browser consent.

Verify and list:

```bash
grok mcp doctor xapi      # ✓ server started, ✓ handshake OK, ✓ tools discovered
grok mcp list
```

#### 2. Grok (web)

Go to `grok.com/connectors` → **New Connector** → **Custom**:

* **Server URL:** `https://api.x.com/mcp`
* **Client ID:** your OAuth 2.0 Client ID
* **Client Secret:** leave blank (Native App)
* **Token Auth Method:** `none` (PKCE only)
* Leave the auto-discovered OAuth endpoints as-is, pick the scopes you want (include `offline.access` for refresh), and complete the X consent screen.

#### 3. Cursor

Create `~/.cursor/mcp.json` (global, all projects) or `.cursor/mcp.json` (this project only). Because `api.x.com/mcp` does not support dynamic client registration, configure Cursor's `auth` object with your own X app's OAuth 2.0 `CLIENT_ID` (with `http://localhost:8787/callback` registered on your X app for Cursor Desktop, and `https://www.cursor.com/agents/mcp/oauth/callback` if signing in from Cursor Web or Cloud Agents). Cursor reads the server's OAuth discovery metadata automatically and authenticates with PKCE:

<CodeGroup>

```json Native OAuth
{
  "mcpServers": {
    "xapi": {
      "url": "https://api.x.com/mcp",
      "auth": {
        "CLIENT_ID": "YOUR_OAUTH2_CLIENT_ID",
        "scopes": ["tweet.read", "users.read", "bookmark.read", "bookmark.write", "offline.access"]
      }
    }
  }
}
```

```json App-only Bearer
{
  "mcpServers": {
    "xapi": {
      "url": "https://api.x.com/mcp",
      "headers": {
        "Authorization": "Bearer YOUR_APP_ONLY_BEARER_TOKEN"
      }
    }
  }
}
```

```json title="xurl bridge (optional)" lines wrap icon="/icons/xds/icon-brackets.svg"
{
  "mcpServers": {
    "xapi": {
      "command": "npx",
      "args": ["-y", "@xdevplatform/xurl", "mcp", "https://api.x.com/mcp"],
      "env": {
        "CLIENT_ID": "YOUR_X_APP_CLIENT_ID",
        "CLIENT_SECRET": "YOUR_X_APP_CLIENT_SECRET"
      }
    }
  }
}
```

</CodeGroup>

Include `"offline.access"` in `auth.scopes` so Cursor receives a refresh token (you can also use `"${env:X_MCP_CLIENT_ID}"` interpolation instead of hardcoding `CLIENT_ID`). Omit `CLIENT_SECRET` for a Native App (public client). Then open **Cursor → Settings → MCP**, sign in when prompted, and confirm **xapi** shows a green dot and its tools.

### Authentication

#### OAuth 2.0 user context (native MCP discovery)

When an unauthenticated client sends `POST https://api.x.com/mcp`, the server responds with `401 Unauthorized` and:

```http
WWW-Authenticate: Bearer resource_metadata="https://api.x.com/.well-known/oauth-protected-resource"
```

Clients follow standard MCP OAuth discovery from there:

1. Fetch Protected Resource Metadata from `https://api.x.com/.well-known/oauth-protected-resource` (or `https://api.x.com/.well-known/oauth-protected-resource/mcp`), which returns `resource: "https://api.x.com/mcp"`, `authorization_servers: ["https://api.x.com"]`, `bearer_methods_supported: ["header"]`, and the supported X API scopes.
2. Fetch Authorization Server Metadata from `https://api.x.com/.well-known/oauth-authorization-server`, which returns `authorization_endpoint: "https://x.com/i/oauth2/authorize"`, `token_endpoint: "https://api.x.com/2/oauth2/token"`, `code_challenge_methods_supported: ["S256"]`, `grant_types_supported: ["authorization_code", "refresh_token"]`, and `token_endpoint_auth_methods_supported: ["none", "client_secret_basic"]`.
3. Run OAuth 2.0 Authorization Code + PKCE (`S256`) using your pre-registered X app's `client_id`. Include `offline.access` in your scopes so tokens refresh automatically.

Because X keeps a single live OAuth grant per `(app, user)`, signing in from a second client with the same app revokes the first client's tokens. Use one X app per client if you connect multiple clients at once.

#### App-only (direct URL)

For read endpoints, you can point a client straight at the URL with a **static App-only Bearer token**. This is useful for clients that support remote MCP with custom headers:

```toml
# ~/.grok/config.toml
[mcp_servers.xapi_direct]
url = "https://api.x.com/mcp"
enabled = true

[mcp_servers.xapi_direct.headers]
Authorization = "Bearer YOUR_APP_ONLY_BEARER_TOKEN"
```

Trade-off: no auto-refresh and no user context (no actions as you). Use OAuth 2.0 user context for full functionality.

#### Optional `xurl mcp` bridge

For clients without native pre-registered-client OAuth support, `xurl mcp` runs locally via `npx` (or an installed `xurl` binary) and exposes a stdio JSON-RPC channel while forwarding requests to `https://api.x.com/mcp`. Resolution order for credentials: **`CLIENT_ID`/`CLIENT_SECRET` env vars → the active app in `~/.xurl`**. The bridge caches tokens in `~/.xurl` and refreshes them automatically (including a forced refresh after a `401`). All diagnostics go to **stderr**; **stdout stays a clean JSON-RPC channel**.

With no cached token, the bridge prints to stderr and opens your browser:

```text
[xurl mcp] no valid OAuth2 token; opening the browser to sign in -- complete the login to start the bridge...
[xurl mcp] authentication complete; starting bridge
```

The MCP handshake is held until you finish — that's why clients using the bridge need a generous `startup_timeout_sec`.

#### Headless / remote machines

No reachable browser? Authenticate once out-of-band with `xurl`, then start the client using the `xurl mcp` bridge:

```bash
# Required: the env block in your client config only applies to the bridge,
# not to manual xurl runs — export the credentials in this shell first.
export CLIENT_ID="YOUR_X_APP_CLIENT_ID"
export CLIENT_SECRET="YOUR_X_APP_CLIENT_SECRET"

xurl auth oauth2 --headless                 # prints an auth URL; you paste back the redirect URL/code
xurl auth oauth2 --app my-app --headless    # for a specific app
```

#### Multiple apps & accounts (`xurl mcp`)

<Note>
The OAuth login authorizes **whichever X account is logged in when the browser opens** — not necessarily the account that owns the app. If you're posting on behalf of a secondary/bot account, switch to that account in your browser before completing the login (or use `-u` with `xurl mcp` to pick a previously authorized user).
</Note>

```bash
xurl --app my-app mcp                  # bridge using a specific registered app
xurl mcp -u alice https://api.x.com/mcp  # act as a specific OAuth2 user
```

In a client config, add `"--app", "my-app"` or `"-u", "alice"` to `args`.

### Read-only mode

Add `?read_only=true` to the MCP URL to make a connection read-only. It works on both the X MCP (`https://api.x.com/mcp?read_only=true`) and the [X Ads MCP](/x-ads-api/mcp) (`https://ads-api.x.com/mcp?read_only=true`).

On a read-only connection:

- **Only read tools are offered.** Tools that post, send messages, or create, change, or delete anything are left out of the tool list.
- **Write tools are refused by the server.** A call to a tool that was left out fails, even if your token has write scopes.
- **The client is told at connect time.** The server's `initialize` response includes instructions saying the connection is read-only, which MCP clients can pass on to the model.

OAuth scopes still apply to the read tools that remain — each one needs the scopes its endpoint requires. A read tool is one that makes a `GET` request to the API, so a tool that uses another method is left out even if it changes nothing (for example, `estimate_audience` on the X Ads MCP).

In any client config above, add the parameter to the URL you already use:

<CodeGroup>

```toml Native OAuth (~/.grok/config.toml)
[mcp_servers.x-readonly]
url = "https://api.x.com/mcp?read_only=true"
enabled = true

[mcp_servers.x-readonly.oauth]
clientId = "YOUR_OAUTH2_CLIENT_ID"
callbackPort = 8080
scopes = ["tweet.read", "users.read", "offline.access"]
```

```json App-only Bearer
{
  "mcpServers": {
    "x-readonly": {
      "url": "https://api.x.com/mcp?read_only=true",
      "headers": {
        "Authorization": "Bearer YOUR_BEARER_TOKEN"
      }
    }
  }
}
```

```json xurl bridge (optional)
{
  "mcpServers": {
    "x-readonly": {
      "command": "npx",
      "args": ["-y", "@xdevplatform/xurl", "mcp", "https://api.x.com/mcp?read_only=true"],
      "env": {
        "CLIENT_ID": "YOUR_X_APP_CLIENT_ID",
        "CLIENT_SECRET": "YOUR_X_APP_CLIENT_SECRET"
      }
    }
  }
}
```

</CodeGroup>

Accepted spellings and values:

| URL ends with | Tools offered |
|---|---|
| `?read_only=true` | Read tools only |
| `?read_only`, `?readonly`, `?READ-ONLY=1`, `?read_only=0` | Read tools only |
| `?read_only=false`, or no parameter | Full tool list |

The name can be `read_only`, `readonly`, or `read-only`, in upper or lower case. Any value other than `false` turns read-only mode on, including no value at all. Only `false` (in any case) or leaving the parameter off gives the full tool list.

### `xurl mcp` bridge configuration reference

These settings apply when using the optional `xurl mcp` local bridge:

| Setting | Where | Notes |
|---|---|---|
| `CLIENT_ID` / `CLIENT_SECRET` | `env` | Your X app credentials (or rely on a registered app in `~/.xurl`) |
| `REDIRECT_URI` | `env` | Overrides the callback; must be registered on the app. Default `http://localhost:8080/callback` |
| `startup_timeout_sec` | client config | Set **≥ 300** so first-run login can complete |
| `[URL]` positional | `args` | Defaults to `https://api.x.com/mcp` |
| `--app NAME` | `args` | Use a specific registered app |
| `-u, --username` | `args` | Act as a specific OAuth2 user |

Advanced env overrides (rarely needed): `AUTH_URL`, `TOKEN_URL`, `API_BASE_URL`, `INFO_URL`.

### Verify & troubleshoot

```bash
# Inspect OAuth discovery metadata directly:
curl -s https://api.x.com/.well-known/oauth-protected-resource
curl -s https://api.x.com/.well-known/oauth-authorization-server

grok mcp doctor xapi          # Grok Build: end-to-end check
# or test the optional xurl bridge by hand (Ctrl-C to exit):
npx -y @xdevplatform/xurl mcp https://api.x.com/mcp
```

| Symptom | Cause / Fix |
|---|---|
| Client times out on startup (`xurl mcp`) | Raise `startup_timeout_sec` to 300+; the bridge is waiting on your browser login |
| Browser never opens (`xurl mcp`) | No display (headless) → run `xurl auth oauth2 --headless` first; ensure `npx` resolves |
| `401` / `token refresh failed` | App credentials wrong, refresh token revoked, or `offline.access` not requested → re-authenticate (or re-run `xurl auth oauth2 [--app NAME]`) |
| Token exchange rejected for confidential app | X supports `none` (PKCE only) and `client_secret_basic`, not `client_secret_post` → switch to a Native App (public client) or configure `client_secret_basic` |
| Browser shows "Something went wrong — You weren't able to give access to the App" | `CLIENT_ID` (and `CLIENT_SECRET` if confidential) missing or invalid → check your client OAuth config or `xurl` env vars |
| Redirect/callback error in browser | Callback URI not registered on the app (e.g. `http://127.0.0.1:8080/callback` for Grok Build CLI, `http://localhost:8787/callback` for Cursor Desktop, `http://localhost:8080/callback` for `xurl`) |
| `client-not-enrolled` after login | App isn't in the right X package/environment → in the console move it to **Pay-per-use** + **Production** |
| `npx` pulls a stale version | A private registry mirror is default → pin `--registry=https://registry.npmjs.org/` in `args` |
| Empty/garbled tool output (`xurl mcp`) | Don't run the bridge with `--verbose`; stdout must stay a clean JSON-RPC channel |

### Security & best practices

- **Treat `~/.xurl` and access tokens as secrets** — don't paste them into chats, logs, or shared configs. Prefer per-project `.mcp.json`/`.grok/config.toml` that reference env vars over committing raw secrets.
- **Use a dedicated app** for MCP with only the scopes you need.
- **Writes count against rate limits** (bookmarks, `article_publish`) and are stricter than reads; expect occasional `429`s and back off.
- **Keep credentials local** — whether connecting directly via OAuth 2.0 PKCE or through the optional `xurl mcp` bridge, requests authenticate over TLS to `api.x.com` with Bearer tokens.

## Docs MCP — documentation search

X hosts an MCP server for the X API documentation at `https://docs.x.com/mcp`. Connect it to your AI tool to search and read documentation pages without leaving your workflow.

### Available tools

| Tool | Description |
|:-----|:------------|
| `search_x` | Search across the X documentation for relevant information, code examples, API references, and guides |
| `get_page_x` | Retrieve the full content of a specific documentation page by its path |

### Configuration

Add the docs MCP server to your MCP client configuration:

```json
{
  "mcpServers": {
    "x-docs": {
      "url": "https://docs.x.com/mcp"
    }
  }
}
```

This is useful when you're building with the X API and want your AI assistant to look up endpoint details, authentication guides, or code examples on the fly.

## OpenAPI specification

The machine-readable API specification for all X API v2 endpoints.

| Resource | URL |
|:---------|:----|
| **OpenAPI Spec (JSON)** | [`https://api.x.com/2/openapi.json`](https://api.x.com/2/openapi.json) |

```bash
curl https://api.x.com/2/openapi.json -o openapi.json
```

You can use it to auto-generate API clients, import into [Postman](https://www.postman.com/xapidevelopers/x-api-public-workspace/collection/34902927-2efc5689-99c6-4ab6-8091-996f35c2fd80), feed into custom AI agents, or validate request/response schemas.
